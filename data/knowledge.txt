# **实验一：大模型平台认知与API调用基础**

## **1.1 实验目的**

- 了解主流大模型平台（DeepSeek、通义千问、Kimi、智谱GLM、OpenAI等）的特点与差异
- 掌握大模型API的认证、调用与参数配置方法
- 掌握提示词工程（Prompt Engineering）的基本技巧

## **1.2 理论基础**

### **1.2.1 大语言模型概述**

大语言模型（LLM）是基于Transformer架构、在海量文本上预训练的生成式模型，具备文本生成、语义理解、推理与工具调用等能力。主流模型包括DeepSeek-V3/R1、通义千问Qwen系列、GLM-4、Kimi、GPT系列等。

### **1.2.2 API调用规范（OpenAI兼容接口）**

国内外主流平台大多提供与OpenAI兼容的REST API，核心要素包括：API Key（身份认证）、Base URL（接口地址）、model（模型名）、messages（对话消息列表）、temperature（采样温度）、max_tokens（最大输出长度）等。

### **1.2.3 提示词工程**

- 角色设定：为模型指定明确的身份与任务边界
- 少样本示例（Few-shot）：通过示例引导输出格式
- 结构化输出：要求模型以JSON/Markdown等格式返回
- 思维链（Chain-of-Thought）：让模型分步推理

## **1.3 实验内容**

### **实验1-1：API基础调用**

【实验说明】本实验完成从零到第一次成功调用大模型API的完整流程，为后续所有实验打下基础。

步骤1：选择一个大模型平台（推荐DeepSeek，注册简单且有免费额度），在控制台创建API Key，并将其保存到环境变量中（如DEEPSEEK_API_KEY），切勿直接写在代码里。

步骤2：安装Python SDK：pip install openai。国内主流平台均采用与OpenAI兼容的接口规范，因此同一份代码只需修改base_url和model即可切换平台。

步骤3：创建OpenAI客户端实例，api_key从环境变量读取，base_url填平台提供的地址（DeepSeek为https://api.deepseek.com）。

步骤4：构造messages消息列表：system消息设定模型角色（如"Python助教"），user消息是本次提问内容。消息列表是理解多轮对话的关键数据结构。

步骤5：调用chat.completions.create并传入model、temperature、max_tokens等参数。返回对象中choices\[0].message.content即为模型回答。建议先打印原始返回对象，观察其完整结构。

预期结果：程序输出一句关于数据挖掘的解释性文字。若出现401错误，检查API Key；若出现余额不足提示，检查平台账户额度。

from openai import OpenAI

\# 以DeepSeek平台为例（其他平台仅需修改base_url与model）

client = OpenAI(

api_key="YOUR_API_KEY",

base_url="https://api.deepseek.com"

)

response = client.chat.completions.create(

model="deepseek-chat",

messages=[

{"role": "system", "content": "你是一位耐心的Python助教"},

{"role": "user", "content": "用一句话解释什么是数据挖掘"}

],

temperature=0.7,

max_tokens=200

)

print(response.choices\[0].message.content)

### **实验1-2：多轮对话与消息历史管理**

【实验说明】本实验实现带上下文记忆的多轮对话功能，这是AI小游戏和问答APP的核心基础。

步骤1：定义全局变量history，并预置一条system消息用于固定助手的身份与行为边界。

步骤2：每次用户输入时，先将用户消息追加到history末尾，再将完整history作为messages传给API。模型会根据完整历史理解上下文。

步骤3：收到回复后，将assistant消息同样追加到history，保证下一轮对话时模型"记得"自己说过的话。

步骤4：测试时连续追问（如"它有哪些应用？"），观察模型能否正确指代上一轮内容。

注意事项：history会随对话轮数线性增长，token费用随之增加。工程实践中通常需要限制历史长度（如只保留最近10轮），本实验先观察完整历史的行为即可。

history = \[{"role": "system", "content": "你是乐于助人的学习助手"}]

def chat(user_input):

history.append({"role": "user", "content": user_input})

resp = client.chat.completions.create(model="deepseek-chat",

messages=history, temperature=0.7)

reply = resp.choices\[0].message.content

history.append({"role": "assistant", "content": reply})

return reply

### **实验1-3：结构化输出与JSON解析**

【实验说明】程序要消费模型的输出，必须让模型返回结构化数据（如JSON），本实验掌握这一关键技能。

步骤1：设计提示词，用明确的格式约定约束输出，例如"仅返回JSON"，并给出目标JSON的键名示例。提示词中同时给出待分析的评论文本。

步骤2：将temperature设为0.0，使采样趋于贪心解码，大幅降低输出格式随机性。部分平台支持response_format参数，可强制JSON模式，建议优先使用。

步骤3：用json.loads将模型返回的字符串解析为Python字典，随后即可像普通数据一样访问sentiment、confidence、keywords等字段。

步骤4：增加健壮性处理——将解析代码放入try/except中，解析失败时打印原始输出以便调试，这在后续小游戏实验中会反复用到。

预期结果：程序输出形如{"sentiment": "正面", "confidence": 0.9, "keywords": \["详细", "例子少"]}的字典。

import json

prompt = (

"请分析以下评论的情感倾向，仅返回JSON：\\n"

'{"sentiment": "正面/负面/中性", "confidence": 0~1, "keywords": \[...]}\\n'

"评论：这个实验指导书写得非常详细，就是例子有点少。"

)

resp = client.chat.completions.create(

model="deepseek-chat",

messages=\[{"role": "user", "content": prompt}],

temperature=0.0,

response_format={"type": "json_object"}   # 部分平台支持

)

result = json.loads(resp.choices\[0].message.content)

print(result)

### **实验1-4：Token统计与成本控制**

【实验说明】API按token计费，本实验学会读取用量字段并估算成本，培养成本意识。

步骤1：在API返回对象中，usage字段包含prompt_tokens（输入token数）、completion_tokens（输出token数）和total_tokens（总数）。注意计数在响应对象的usage属性中，而非choices里。

步骤2：登录平台官网查询所用模型的单价（通常按每百万token计价，输入与输出单价不同）。

步骤3：按公式估算单次调用成本：输入token/1,000,000 × 输入单价 + 输出token/1,000,000 × 输出单价。

步骤4：批量测试多条评论分析请求，统计总token消耗与预估总成本，思考如何在提示词层面节省token（如精简system消息、控制max_tokens）。

usage = resp.usage

print(f"输入token: {usage.prompt_tokens}, 输出token: {usage.completion_tokens}")

\# 估算成本 = 输入token/1M * 输入单价 + 输出token/1M * 输出单价

# **实验二：AI小游戏开发**

## **2.1 实验目的**

- 掌握将大模型API集成到交互式程序中的方法
- 理解大模型在游戏场景中的应用：剧情生成、NPC对话、智能出题、游戏裁判
- 掌握控制台/图形界面小游戏的基本开发流程

## **2.2 理论基础**

### **2.2.1 大模型赋能游戏的典型场景**

- 文字冒险游戏：大模型实时生成剧情分支与场景描述
- AI出题官：根据知识点自动生成谜题、成语接龙、猜谜语
- 智能NPC：基于角色设定的多轮对话
- 游戏裁判：判定答案正确性、解释规则、给出提示

### **2.2.2 游戏循环设计**

典型的AI小游戏由"输入→调用大模型→解析输出→更新游戏状态→渲染"的循环构成。游戏状态（State）建议用字典或类维护，便于保存分数、回合数、剧情进度等信息。

## **2.3 实验内容**

### **实验2-1：AI文字冒险游戏**

【实验说明】本实验开发一款由大模型实时生成剧情的文字冒险游戏，综合练习system提示词设计、JSON状态管理与多轮对话。

步骤1：精心设计system提示词（SYSTEM_PROMPT）。这是游戏成败的关键：需要明确规定GM的身份、剧情长度限制（100字以内）、每轮必须给出3个选项、JSON返回格式以及游戏结束条件。提示词越具体，生成越稳定。

步骤2：定义adventure_turn函数，接收客户端、对话历史和玩家行动。将玩家行动包装成user消息追加到history，连同system消息一起发送。

步骤3：使用response_format强制JSON输出，并用json.loads解析得到story（剧情文本）、options（选项列表）和game_over（结束标志）。

步骤4：将模型的原始回复也追加到history，使模型了解自己上一轮生成的剧情，保持世界观一致。

步骤5：编写主循环：打印剧情与选项 → 等待玩家输入行动 → 调用adventure_turn → 若game_over为true则结束游戏并给出结局。

调试建议：若模型偶尔不返回合法JSON，可在解析失败时将错误信息反馈给模型要求重新生成（自我纠错重试）。

import json

SYSTEM_PROMPT = """你是一款文字冒险游戏的GM（游戏主持人）。

规则：根据玩家的行动生成100字以内的剧情，并在结尾给出3个选项，

严格返回JSON：{"story": "...", "options": \["...", "...", "..."]}

若玩家死亡则设置 "game_over": true"""

def adventure_turn(client, history, action):

history.append({"role": "user", "content": f"玩家行动：{action}"})

resp = client.chat.completions.create(model="deepseek-chat",

messages=\[{"role": "system", "content": SYSTEM_PROMPT}] + history,

temperature=0.9, response_format={"type": "json_object"})

state = json.loads(resp.choices\[0].message.content)

history.append({"role": "assistant", "content": resp.choices\[0].message.content})

return state

### **实验2-2：AI猜谜/成语接龙游戏**

【实验说明】本实验实现"AI出题—玩家作答—AI裁判"的完整游戏闭环，重点练习用低温度保证裁判的公正与稳定。

步骤1：实现ai_quiz函数。提示词中明确主题（topic）和难度（difficulty）两个变量，要求返回包含question、answer、hint三个字段的JSON。玩家答不出时可消耗积分换取hint提示。

步骤2：实现judge函数。将题目、正确答案和玩家回答一并交给模型判定，要求返回correct布尔值和comment点评。注意裁判任务需要确定性，temperature必须设为0.0，且给出完整上下文避免模型凭空猜测答案。

步骤3：编写主循环：调用ai_quiz出题 → 玩家输入回答 → 调用judge判定 → 根据correct更新积分 → 询问是否继续下一题。

步骤4：成语接龙变体：将judge的逻辑改为"判断用户成语是否以上一个成语的最后一字开头"，体会提示词逻辑设计对游戏玩法的影响。

对比思考：出题用高温（1.0）保证题目多样性，裁判用低温（0.0）保证判定稳定——这是游戏中"生成与判定分离"的典型温度策略。

def ai_quiz(client, topic, difficulty):

prompt = f"围绕主题【{topic}】生成一道{difficulty}难度的猜谜题，"

# **实验四：AI智能体与RAG知识库应用开发**

# **4.1 实验目的**

- 理解RAG（检索增强生成）的基本原理与 pipeline
- 掌握Embedding向量化、向量检索与提示词拼接的方法
- 掌握使用Streamlit快速开发AI应用（APP）并部署的方法

# **4.2 理论基础**

## **4.2.1 RAG架构**

RAG（Retrieval-Augmented Generation，检索增强生成）通过"检索→增强→生成"三步，让大模型基于私有知识库回答问题，缓解幻觉问题。核心组件：文档切分（Chunking）、向量化（Embedding）、向量数据库（FAISS/Chroma）、重排与生成。

## **4.2.2 Embedding与相似度检索**

Embedding将文本映射为稠密向量，语义相近的文本在向量空间中距离更近。常用相似度度量：余弦相似度。

## **4.2.3 AI应用界面开发**

Streamlit/Gradio允许用纯Python快速构建Web应用，适合课程实训与原型开发；生产环境可进一步使用Flask/FastAPI + 前端框架。

# **4.3 实验内容**

## **实验4-1：文档加载与切分**

【实验说明】RAG的第一步是将知识文档切分为适合检索的文本块（chunk），切分质量直接决定问答效果。

步骤1：准备一份不少于5000字的私有知识文档（如课程讲义、校规、产品手册），以纯文本（.txt）或Markdown格式保存，注意清除无关的页眉页脚与格式符号。

步骤2：安装切分工具：pip install langchain-text-splitters。

步骤3：使用RecursiveCharacterTextSplitter进行递归切分：优先按段落边界切，段落过长时再按句子切。chunk_size=300表示每块约300字符，chunk_overlap=50表示相邻块重叠50字符——重叠可保证语义在块边界处不被割裂。

步骤4：打印切分后的块数，并抽查若干块确认切分边界合理（如"第X章"标题未被拦腰截断）。

from langchain_text_splitters import RecursiveCharacterTextSplitter

with open("knowledge.txt", encoding="utf-8") as f:

text = f.read()

splitter = RecursiveCharacterTextSplitter(chunk_size=300, chunk_overlap=50)

chunks = splitter.split_text(text)

print(f"共切分为 {len(chunks)} 个片段")

## **实验4-2：向量化与FAISS索引**

【实验说明】将文本块转为向量并建立索引，使语义检索成为可能。本实验完全在本地运行，不消耗API费用。

步骤1：安装依赖：pip install sentence-transformers faiss-cpu。首次运行会自动下载Embedding模型（BAAI/bge-small-zh-v1.5，约100MB，中文效果好）。

步骤2：调用model.encode将实验4-1的chunks批量编码为向量，设置normalize_embeddings=True使向量模长为1——此时向量内积在数学上等价于余弦相似度。

步骤3：创建FAISS索引。IndexFlatIP是精确内积索引（数据量小于百万级时足够用且无需训练），将向量转为float32后批量add进索引。

步骤4：保存chunks列表与索引的对应关系（chunks\[i]与索引中第i个向量一一对应），供检索时回取原文。

验证：随便选第3个块的向量与自身做点积，结果应接近1.0，说明索引建立正确。

from sentence_transformers import SentenceTransformer

import faiss

import numpy as np

model = SentenceTransformer("BAAI/bge-small-zh-v1.5")

embeddings = model.encode(chunks, normalize_embeddings=True)

index = faiss.IndexFlatIP(embeddings.shape\[1])   # 内积（等价于余弦相似度）

index.add(embeddings.astype(np.float32))

## **实验4-3：检索增强问答**

【实验说明】本实验实现RAG的核心链路：问题向量化 → 检索最相关文本块 → 拼接进提示词 → 大模型生成有据可查的回答。

步骤1：将用户问题用同一个Embedding模型编码（务必与知识库使用同一模型，否则向量空间不一致），并在FAISS索引中检索top_k=3个最相似块。

步骤2：按检索结果ids从chunks中回取原文，用空行拼接为context。top_k取值需要权衡：过小可能检索不全，过大会引入无关内容干扰模型并增加token开销。

步骤3：构造增强提示词，关键指令是"请仅根据以下资料回答问题，若资料不足请如实说明"——前半句约束模型 grounding 在资料上，后半句防止模型在资料不足时编造（幻觉）。

步骤4：以较低temperature（0.1）调用大模型，同时返回答案和引用来源列表，供界面展示和人工核查。

测试方法：先问一个知识库内的问题（应准确回答），再问一个库外问题（应坦诚说明资料不足而非瞎编），两者都通过才算成功。

def rag_answer(client, question, top_k=3):

q_emb = model.encode(\[question], normalize_embeddings=True)

scores, ids = index.search(q_emb.astype(np.float32), top_k)

context = "\\n\\n".join(chunks\[i] for i in ids\[0])

prompt = (f"请仅根据以下资料回答问题，若资料不足请如实说明。\\n\\n"

f"【资料】\\n{context}\\n\\n【问题】{question}")

resp = client.chat.completions.create(model="deepseek-chat",

messages=\[{"role": "user", "content": prompt}], temperature=0.1)

return resp.choices\[0].message.content, \[chunks\[i] for i in ids\[0]]

## **实验5-3：评估与迭代**

【实验说明】用"大模型当裁判（LLM-as-Judge）"的思路建立简单的自动评估流程，摆脱纯人工试用的主观性。

步骤1：编写不少于10条测试用例，覆盖核心功能、边界情况（空输入、超长输入、无关问题）和典型用户场景，并为每题准备参考答案。

步骤2：实现llm_judge函数：将问题、参考答案、待评答案交给大模型，从准确性、完整性、相关性三个维度1~5分打分并要求给出理由，temperature设为0保证评分稳定。

步骤3：批量跑全部测试用例，汇总评分表，定位低分用例的共同特征（如某类问题提示词覆盖不足）。

步骤4：针对性修改提示词或检索策略后重新评估，对比改进前后平均分，将过程记录进报告的"结果分析"章节——评估-迭代的证据链是报告的重要加分项。

\# 简单的自动评估示例：让大模型当裁判

def llm_judge(client, question, answer, reference):

prompt = (f"【问题】{question}\\n【参考答案】{reference}\\n"

f"【待评答案】{answer}\\n请从准确性、完整性、相关性"

"三方面1-5分评分并说明理由，返回JSON。")

resp = client.chat.completions.create(model="deepseek-chat",

messages=\[{"role": "user", "content": prompt}], temperature=0.0,

response_format={"type": "json_object"})

return json.loads(resp.choices\[0].message.content)
